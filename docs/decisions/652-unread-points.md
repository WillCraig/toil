# Unread points are not zero (#652)

- **One rule, in core.** `src/core/brief/points.ts` holds `pointsOf`, `sumPoints` and `pointsPhrase`. The briefing by code and Toil UI both use it, so the CLI's `projects brief` and the Summary tab can't word the same total two ways. An item with no estimate in points counts as unread, whatever the reason: the tracker holds none, the toil project doesn't name the field, or it is estimated in hours.
- **A set where nothing was read has no total** (`points: null`). A set with some read sums those and counts the rest (`unestimated`). A real estimate of 0 is read and counts as 0. An empty set is a real 0: there was nothing to read.
- **Sentences leave an unread figure out, or say "no points were read".** The Summary's "can't start" card says "No points were read for them." instead of "Together they are 0 points", and "Together they are 8 points; no points were read for 1 of them." when only some are read. A parenthetical count becomes "(5 points, and 2 items with no points read)", or nothing when none were read. "No points were read" is true both when the tracker holds none and when the field isn't named, which is the demo's case.
- **Sprint tallies (`Tally`) carry `points: number | null` and `unestimated`**, and `Health` gains `scope`, the tally of every item in the sprint. `sprintPoints(h)` gives done, left and total, or null when no item in the sprint has points. Once any points are read, done and left split them, so a side with no points of its own shows a real 0 of them; the items with none are said in the notes. That is a reading of the points that exist, not a guess.
- **Screens:** Flow's sprint figures show the dash (`Unread`) with "no points read, N items", or the figure with ", N items with no points read"; the meter and the realm theme's bar hide when unknown. The burn-up with no points read is an empty state whose action is **Name the points field** (Toil project setup: Find the fields for a Jira toil project, which reads only Jira, else the field names), with a new flavour key `empty.points` worded by every theme; with some read, the legend says how many items aren't drawn. The Overview tile, the project card's sprint line and mini burn-up, the overworld gem counter and the briefing history's sprint line say "no points read" or a dash. The Gantt's critical chain and the worklog's "sprint ended" line say how many items had no points read.
- **Core's briefing reads null for unread points: the maintainer's call, 2026-11-17.** `BriefItem.holds.points` and `SprintFacts.points.total`, `done` and `left` are `null` when none of the items has points read (real zeros stay 0), and both gain `unestimated`. Principle 12 asks for null in an envelope; principle 7 would call 0 becoming null a different result, but the maintainer ruled it isn't counted as breaking while toil has no users really yet, so it ships as a `fix:` with no `BREAKING CHANGE` and no contract version bump, and the PR says plainly what now reads null. The sprint lens skips when the total is null, with the note "No points were read for any item in the sprint.", and runs on a sprint of real 0-point estimates. The sprint reason's text adds "N items with no points read are left out." when some are. Ordering reasons by points held treats null as weighing nothing, for the order only.
- **The briefing history's snapshot** keeps `sprint` for a running sprint and makes its figures null when no points were read, so an older saved snapshot (numbers) still reads.
- **A sprint of real 0-point estimates gets its own status** (review round 1): **No points to measure**, "the stories in the sprint are estimated at 0 points, so progress can't be measured." The figure is a real reading, but "all 0 points are done" would call a sprint of open stories finished.
