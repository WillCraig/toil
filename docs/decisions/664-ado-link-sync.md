# Azure DevOps link changes in Toil UI's sync (#664)

Defaults this PR chose; the maintainer's decisions on #664 are not repeated.

## toil

- **The command is `ado work-item link-feed`, on both deployments, with `--updated-since`, `--limit` and `--cursor`.** It sits beside `work-item feed` (the revision feed) under `work-item`, and is named after it so the two read as a pair; `work-item link` is the write that adds a link, so the read could not take that name, and `work-item links` (the `comment`/`comments` pattern) would read as one item's links, as `comments <id>` is one item's comments, when this is the whole project's. `--updated-since` is the area's "changed since" flag, with the same date forms and the same `wiqlInstant` check. No `--link-types` or `--types` flag: the caller narrows with `--select`, and the sync wants every link type (principle 3, few options).
- **Data is the feed's `values`, as Azure DevOps sends them**: `{ rel, attributes: { linkType, sourceId, targetId, isActive, changedDate, changedOperation, changedBy, comment, sourceProjectId, targetProjectId } }`, a removal reported with `isActive: false` and `changedOperation: "remove"`. That is the shape a live read of Azure DevOps Services returned on the sandbox (2026-11-18), not the flat record of the reference's example, so the fixtures are that capture, sanitized, and toil passes it through unreshaped (`data` is the API's own shape). Toil UI reads `attributes` and falls back to the flat form, in case Server sends what the reference shows. Paging is the revision feed's, shared in `src/areas/ado/feed.ts` (`feedPages` is now generic over the record type): `startDateTime` on the first request only, `continuationToken` after, not followed once `isLastBatch` is true. Ten-minute time limit, as the revision feed has.
- **Requests**: Services `{org}/{project}/_apis/wit/reporting/workitemlinks?api-version=7.1[&startDateTime=…]`, Server `{collection}/{project}/_apis/wit/reporting/workitemlinks?…`, both `GET`.
- **Additive**: `docs/command-contract.json` and the divergences gain nothing, as with `work-item feed` (#511).
- **API facts relied on, from Microsoft's public reference** (https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/reporting-work-item-links/get?view=azure-devops-rest-7.1): the URI; `startDateTime`, `continuationToken`, `linkTypes`, `types`; the response `values`, `continuationToken`, `isLastBatch`, `nextLink`; a link record's `rel`, `sourceId`, `targetId`, `changedDate`, `isActive`, `changedOperation`. The fixtures are the live Services capture, sanitized (below); the reference's flat example was not what Services sent.
- **Verified live on Azure DevOps Services** (the `Toil Sandbox` project, read-only): the request, the nested shape above, and the seven blocks-link removals of the 14:52 UTC reseed reported with `isActive: false` (#152→#156 and #156→#160 among them), while those items kept their revision and ChangedDate.
- **Unverified, appended to the Azure DevOps suspected-bug issue (#69):** (1) that Server sends the same nested shape and reports a removal the same way; (2) whether `startDateTime` compares `changedDate` and whether it is strict (the sync's five-minute margin covers either); (3) that a link between items in two projects is reported to the project-scoped feed of either end.

## Toil UI

- **The link feed is read only beside an incremental `ado work-item search`**, with the search's own input less `wiql`, from the same watermark. Both ends of every link change join the source's changed items, so `get-many` reads them again. A first read has no watermark and reads `get-many` whole anyway.
- **The link feed is the sync's own call, not the dashboard's**: it is not stored in the cache, not in `READ_COMMANDS`, and a failure does not mark the source failed, because the data is still read correctly: the sync says so in its messages and reads every `get-many` slice whole that run.
- **On the day the search is listed whole (`RECONCILE_MS`), `get-many` is read whole too**, whatever the link feed said: the fallback the issue asked for, and the guard against anything the feed misses. The ids-only listing stays ids only.
- **A link between items in two projects of one toil project may wait for the daily re-read.** Each project's search, link feed and `get-many` run in their own task, concurrently. If such a link is reported only to the other project's feed (unverified point 3), that feed may land after this project's `get-many` has run, and the daily whole read is what corrects it. Not tested with two projects: the sample has no toil project with two Azure DevOps projects, and building one for this case was out of proportion to a day's delay the reconcile already bounds.
- **Histories are unaffected.** An item whose links changed joins the changed set, so if it is one the revision feed doesn't hold whole it is read with `work-item history` again; a link change adds no revision, so that costs a call and changes nothing.
- **Pinning.** Toil UI from this commit asks for `ado work-item link-feed`, which the pinned toil doesn't have yet. Against it the call fails with an unknown command, the sync says so and reads `get-many` whole each sync, which is correct and costs a few batch requests; the failure is said in each sync's messages and nowhere more lasting, a cost in requests, not in what the views show; a `toil-ui-v…` release goes out with or after the toil release that has the command.
