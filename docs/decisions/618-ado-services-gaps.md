# The Azure DevOps Services commands demo seeding needed the raw API for (#618)

- **Six gaps, six commands, all on a `deployment: cloud` connection.** Seeding the Services sandbox on 2026-11-16 went through `ado api` for each, and the standing rule (2026-11-16) is that a needed passthrough call is a missing command. `repo create` and `work-item assign` are Services implementations of Server's recorded commands, with the same path, flags and words, so one tool serves both. `sprint update`, `commit create` and `work-item delete-comment` are new and Services-only, so a Server connection gets `UNSUPPORTED` before any request. `work-item link` gains a Services implementation with `--pr`, and `pr create` gains `--work-item`; both flags are Services-only.
- **`docs/command-contract.json` is unchanged.** The brief said to record the new paths there, but the contract's `ado` rows record Azure DevOps Server, as its `jira` and `bitbucket` rows record Data Center, and every Services addition so far (`sprint list`, `pr threads`, `--rev`) is listed in `docs/command-contract.md` instead. The new commands and flags are added there, in a new `ado` paragraph beside Jira's and Bitbucket's. Adding Services-only rows to the JSON would make the contract test require them of Server, which has none of them.
- **`sprint update <sprint>` writes the project's iteration tree, not the team's settings.** Azure DevOps keeps a sprint's dates on the iteration (a classification node); the team only selects it. So the command reads the tree once and finds the sprint by its id (the GUID `sprint list` prints, which is the node's `identifier`), its path (`Imagile\Sprint 1`, as `sprint list` prints it, or the node's own `\Imagile\Iteration\Sprint 1`), or its name when only one iteration has it, then patches it by its path under the root. It takes no `--team`, since the change is project-wide, and the skill page says every team that selected the sprint sees it. The flags are Jira's `sprint update` flags where the idea is the same (`--name`, `--start`, `--end`); there is no `--goal`, which Azure DevOps doesn't have.
- **Sprint dates are days.** A date or date-time is sent as midnight UTC of the calendar date as written (`2026-11-27T17:00:00-05:00` is the 27th), since Azure DevOps keeps whole days and a converted UTC instant could land on the day before or after. Given only `--start` or `--end`, the other is kept from the sprint, because the API sets the two together; with neither on the sprint, it's `INVALID_INPUT` asking for both.
- **`commit create` is the name** (the maintainer's call on #618, 2026-11-16, over the first draft's `repo commit`). `commit` is already a resource in `ado` (`commit status <commit>`), the thing you hold an id for, and the Command Shape puts a verb after it. Not `push`: the API is Pushes, but `push` reads as sending local git commits, which this doesn't.
- **`commit create --file <path>` commits a workspace file at the same relative path in the repository**, repeatable, rather than a `<repo path>=<local path>` mapping. It reads through `ctx.files`, so the workspace bound holds, and refuses an absolute path, a `..` part or a file named twice before anything is sent. Every file is read before the first request, so a missing one stops the commit whole. Content goes base64-encoded, so binary files work. Each change is an `edit` where the base commit already has that path and an `add` where it doesn't, read from one recursive item listing of the base, scoped to the deepest folder holding every committed file, because the server refuses the other way round. A commit at the repository root still lists the whole tree, which is fine for the repositories this was built for and costs one larger read on a big one. There is no delete or rename: nothing needed one, and adding them is additive later.
- **A new branch starts from `--from`, else the repository's default branch, else nothing.** The ref update names the commit the branch moves from: its own head, a new branch's starting commit, or the zero object id for the first commit of an empty repository, which is how the stopgap created `main` and branched from it. A `--from` that doesn't exist is `NOT_FOUND` before the push. `refs?filter=` is a prefix match, so the exact ref name is picked from the answer (`heads/main` also matches `heads/main-old`).
- **`work-item link` on Services takes `--target` or `--pr`, not both.** `--target` is text, as Server's recorded flag is: the one MCP tool's schema for a field both deployments take is Server's, so an MCP caller sends a string, and Services checks it is a number itself. `--pr` adds the `ArtifactLink` the web UI's Development section adds (`vstfs:///Git/PullRequestId/<project id>%2F<repo id>%2F<pr id>`), reading the repository once for the two ids. `--type` with `--pr` is refused, since a pull request link has one kind. The command's description and tool description are worded once for both in `overrides.ts`.
- **`pr create --work-item <id>` as well as `work-item link --pr`.** The brief offered either; both are small, and they answer different moments: linking as the pull request opens (the API's `workItemRefs`), and linking one that already exists, which is what the seeding needed.
- **`work-item delete-comment <id> <comment-id>` mirrors Server's `pr delete-comment`**: the same verb, positional ids, `{ "deleted": true }`, `mcp: false`, and `IN_PROJECT`, since the comments API lives under the project. It sends `api-version=7.1-preview.4`, the only version the comments API has at 7.1.
- **No live run of `repo create`** against the sandbox. There is no `repo delete` (a delete would be CLI only, and isn't asked for), so a check would leave an empty repository in the project the launch videos record from 18 November. Its request is the stopgap's, which ran there on 2026-11-16.
- **`--from` keeps its name on `commit create`** (the maintainer agreed, 2026-11-16), though `work-item categorize --from` reads a plan file: Bitbucket's branch create already says `--from <ref>` for where a branch starts, and a branch is the idea here. One flag naming different things in different commands is a question for the flag standardization that follows this PR.
- **`--file` stays for now.** It is the Command Shape's flag for a file to upload, which a commit is. The maintainer wants one global file-input parameter that works the same everywhere (2026-11-16); that standardization is its own change, and moves this flag with every other.
- **A date-time given to `sprint update` warns** (`ADO_SPRINT_DAY`, the maintainer agreed, 2026-11-16) that only its calendar date was kept, so the dropped time and zone are said in the envelope, not only in the docs (principle 4).
- **Left as they are, with the maintainer's agreement (2026-11-16):** `commit create` is served over MCP, so with writes on an agent can commit straight to a default branch, inside the usual two-step gate; there is no size bound on the files it sends, as there is none on attachment uploads; and Services-only commands stay recorded in `docs/command-contract.md` prose.
