# JWT decode suspected bugs (#75)

- **Items 1, 2 and 3 are fixed** as divergences under principle 4 (`docs/divergences/jwt.json`). A local run of `decodeJwt` on the issue's crafted tokens confirmed each one: JSON that was not an object was accepted, Node's base64 decoder skipped characters outside the alphabet, and invalid UTF-8 became U+FFFD. The header and payload now have to be base64url, UTF-8, and a JSON object.
- **Trailing `=` padding is still accepted.** RFC 7515 appendix C allows it, and `util encode`'s base64url decoder already does. Whitespace is not skipped, unlike that decoder: a JWT segment has none (RFC 7519 §7.2), so the encode codec was not reused.
- **The signature segment is still not checked.** Item 2 notes that any signature string comes back verbatim. The command returns that text and does not verify signatures, so the alphabet check covers only the two segments it decodes. A trailing newline in an argument therefore stays in `data.signature`.
- **Item 4 is refuted and kept.** The suggested change was to accept a `Bearer ` prefix and trim whitespace so the decode succeeds. The check showed the old behaviour, and it stays: the prefix is still an error (now `header is not valid base64url`, because item 2 sees the space), and trailing whitespace stays in the signature. RFC 7519 §7.2 says to reject extra characters rather than drop them, the fix text already names the prefix, and `jwt decode -` already drops one trailing line ending.
